# Лабораторная работа №10
## Entity Framework Core: сервер пишет в базу данных

**Студент:** Дудин Семен Дмитриевич

## 1. Цель работы

Подключить ASP.NET Core к PostgreSQL с помощью Entity Framework Core, реализовать постоянное хранение заявок и проверить сохранение данных после перезапуска сервера.

## 2. Используемые технологии

- .NET 10;
- ASP.NET Core Web API;
- Entity Framework Core 10;
- Npgsql.EntityFrameworkCore.PostgreSQL;
- PostgreSQL 16.4;
- dotnet-ef;
- терминал macOS.

Создана отдельная база данных `multimedia_repair_lab10`.

## 3. Настройка подключения

Установлены пакеты `Microsoft.EntityFrameworkCore.Design` и `Npgsql.EntityFrameworkCore.PostgreSQL`.

Строка подключения настроена через .NET User Secrets. Пароль PostgreSQL не хранится в исходном коде и не добавляется в репозиторий.

## 4. Модель данных

Создан контекст `Data/AppDbContext.cs` и модели:

- `RepairRequest` — заявка на ремонт;
- `Classroom` — аудитория;
- `User` — пользователь системы.

Настроены таблицы `repair_requests`, `classrooms`, `users`, первичные и внешние ключи, ограничения статусов и индексы.

Добавлены тестовые аудитории с ID 205, 210, 215 и пользователи с ID 5, 6, 7.

## 5. Миграции EF Core

Создана миграция `InitialCreate`:

`dotnet ef migrations add InitialCreate`

Миграция применена командой:

`dotnet ef database update`

Проверено создание таблиц `classrooms`, `users`, `repair_requests` и `__EFMigrationsHistory`.

## 6. Интеграция с ASP.NET Core

В `Program.cs` зарегистрирован `AppDbContext` с провайдером Npgsql.

Сервис `RepairRequestService` переведён с хранения данных в оперативной памяти на Entity Framework Core.

Реализованы асинхронные операции создания, получения, назначения исполнителя и изменения статуса.

Сохранены API-маршруты:

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/api/repair-requests` | Создание заявки |
| GET | `/api/repair-requests` | Получение списка |
| GET | `/api/repair-requests/{id}` | Получение по ID |
| PATCH | `/api/repair-requests/{id}/assignee` | Назначение исполнителя |
| PATCH | `/api/repair-requests/{id}/status` | Изменение статуса |

Удаление заявок через API не реализовывалось.

## 7. Проверка API

Проверена доступность сервера через `/health` — получен HTTP 200.

Выполнены запросы:

- POST — создание заявки, HTTP 201 Created;
- GET списка — HTTP 200 OK;
- GET по ID — HTTP 200 OK;
- PATCH назначения исполнителя — HTTP 200 OK;
- PATCH изменения статуса — HTTP 200 OK.

Созданная заявка:

| Поле | Значение |
|---|---|
| ID | 1 |
| Номер | 1001 |
| Аудитория | 205 |
| Автор | 5 |
| Исполнитель | 7 |
| Статус | InProgress |

## 8. Проверка сохранения данных

После создания заявки и изменения её статуса сервер был остановлен и запущен повторно.

Повторный запрос `GET /api/repair-requests/1` вернул HTTP 200 OK. Заявка сохранилась со статусом `InProgress` и исполнителем с ID 7.

Это подтверждает, что данные хранятся в PostgreSQL и не теряются после перезапуска приложения.

- ASP.NET Core подключён к PostgreSQL.
