# Лабораторная работа №11
## Вход в систему и разграничение прав доступа

### Цель работы

Реализовать механизм аутентификации пользователей в системе обработки заявок на ремонт мультимедийного оборудования и разграничить права доступа в зависимости от назначенной роли. Проверить защиту API от несанкционированных запросов, хранение паролей и безопасность пользовательского ввода.

### 1. Реализация аутентификации

В серверной части реализован контроллер AuthController, отвечающий за вход, проверку текущего пользователя и выход из системы.

Для входа используется POST-запрос `/api/auth/login`. Пользователь передаёт логин и пароль. Сервер проверяет учетные данные и при успешной аутентификации формирует Cookie с информацией о пользователе и его роли.

Для хранения состояния авторизации используется Cookie Authentication. Cookie настроена с параметрами HttpOnly и SameSite, срок действия авторизации составляет 8 часов.

Также реализованы следующие endpoints:
- POST `/api/auth/login` — вход пользователя;
- GET `/api/auth/me` — получение информации о текущем авторизованном пользователе;
- POST `/api/auth/logout` — завершение сеанса.

### 2. Хранение паролей

Для защиты паролей используется PasswordHasher из ASP.NET Core Identity. Пароли пользователей не сохраняются в базе данных в открытом виде. При входе выполняется проверка введённого пароля по сохранённому хешу.

В ходе проверки базы данных PostgreSQL установлено, что пароли диспетчера и техника имеют хешированный формат. У пользователя teacher поле пароля пустое, поэтому авторизация под этой учетной записью невозможна до установки пароля.

### 3. Разграничение прав доступа

Для ограничения доступа к API применяются атрибуты Authorize и проверки ролей пользователей.

Диспетчер имеет право создавать заявки и назначать исполнителей. Техник может изменять статус заявки, только если она назначена именно ему. Гостям доступ к защищённым endpoint запрещён.

Матрица прав доступа вынесена в отдельный файл `docs/role-matrix.md`.

### 4. Проверка доступа к API

В ходе тестирования выполнены запросы к API с разными уровнями доступа.

| Проверка | Результат |
|---|---|
| Запрос списка заявок без авторизации | 401 Unauthorized |
| Создание заявки без авторизации | 401 Unauthorized |
| Создание заявки от имени техника | 403 Forbidden |
| Создание заявки диспетчером | 201 Created |
| Назначение исполнителя диспетчером | 200 OK |
| Изменение статуса назначенной заявки техником | 200 OK |
| Изменение статуса неназначенной заявки техником | 403 Forbidden |

В результате проверок подтверждено, что сервер блокирует неавторизованные запросы и действия, не разрешённые текущей ролью пользователя.

### 5. Проверка защиты от XSS

Для проверки безопасности пользовательского ввода в описание заявки была добавлена строка `<script>alert(1)</script>`.

После создания заявки введённое содержимое отображалось на странице как текст. JavaScript-код не выполнялся, всплывающее окно не появлялось.

Для вывода данных используется стандартная интерполяция Vue, которая экранирует HTML-содержимое. Вставка пользовательского текста через `v-html` не применяется.

### 6. Результат работы

В ходе лабораторной работы реализована аутентификация пользователей, добавлена проверка ролей на серверной стороне, ограничен доступ к операциям с заявками, настроено хеширование паролей и проведена проверка защиты от XSS.

Все основные проверки доступа завершились ожидаемыми HTTP-кодами. Реализованные механизмы позволяют ограничить операции пользователей в соответствии с их ролями и предотвращают несанкционированное изменение заявок.

### Вывод

Проверена работа аутентификации, ограничения доступа к API, защита паролей и безопасность отображения пользовательских данных. Поставленные цели лабораторной работы достигнуты.
