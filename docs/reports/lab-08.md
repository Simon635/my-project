
# Лабораторная работа №8
## REST API: создание, чтение, назначение исполнителя и изменение статуса заявок

### 1. Цель работы

Цель лабораторной работы — разработать REST API для управления заявками на ремонт мультимедийного оборудования с использованием ASP.NET Core Web API.

В рамках работы необходимо реализовать создание и получение заявок, назначение исполнителей, изменение статусов, валидацию входных данных и обработку ошибок HTTP.

### 2. Используемые технологии

- C#
- ASP.NET Core Web API
- .NET 10
- Visual Studio Code
- Terminal (macOS)
- curl
- Postman

### 3. Структура проекта

Для реализации функциональности были созданы следующие компоненты:

- `Models/RepairRequest.cs` — модель заявки на ремонт.
- `Dtos/CreateRepairRequestRequest.cs` — DTO для создания заявки.
- `Dtos/RepairRequestResponse.cs` — DTO ответа API.
- `Dtos/AssignRepairRequestRequest.cs` — DTO назначения исполнителя.
- `Dtos/UpdateRepairRequestStatusRequest.cs` — DTO изменения статуса.
- `Services/IRepairRequestService.cs` — интерфейс сервиса.
- `Services/RepairRequestService.cs` — реализация бизнес-логики.
- `Controllers/RepairRequestsController.cs` — REST-контроллер.

Сервис зарегистрирован в контейнере зависимостей ASP.NET Core с использованием Singleton.

### 4. Реализация модели заявки

Модель `RepairRequest` содержит следующие поля:

| Поле | Тип | Описание |
|---|---|---|
| Id | int | Уникальный идентификатор |
| Number | int | Номер заявки |
| Title | string | Название заявки |
| Description | string | Описание неисправности |
| Status | string | Текущий статус |
| ClassroomId | int | Номер аудитории |
| CreatedByUserId | int | Идентификатор автора |
| AssigneeUserId | int? | Идентификатор исполнителя |

Идентификаторы и номера заявок генерируются автоматически. Начальный номер заявки — 1001.

Для демонстрации работы API автор заявки задаётся тестовым значением `CreatedByUserId = 5`.

### 5. Реализация REST API

Был создан контроллер `RepairRequestsController` с маршрутом `/api/repair-requests`.

Реализованы следующие endpoints:

| HTTP-метод | Маршрут | Назначение |
|---|---|---|
| POST | `/api/repair-requests` | Создание заявки |
| GET | `/api/repair-requests` | Получение списка заявок |
| GET | `/api/repair-requests/{id}` | Получение заявки по идентификатору |
| PATCH | `/api/repair-requests/{id}/assignee` | Назначение исполнителя |
| PATCH | `/api/repair-requests/{id}/status` | Изменение статуса |

#### 5.1. Создание заявки

Для создания заявки используется POST-запрос.

Пример тела запроса:

```json
{
  "title": "Не работает проектор",
  "classroomId": 205,
  "description": "Проектор не включается после подачи питания"
}
```

После успешного создания сервер возвращает HTTP 201 Created и объект созданной заявки.

Пример ответа:

```json
{
  "id": 1,
  "number": 1001,
  "title": "Не работает проектор",
  "description": "Проектор не включается после подачи питания",
  "status": "New",
  "classroomId": 205,
  "createdByUserId": 5,
  "assigneeUserId": null
}
```

#### 5.2. Получение заявок

Реализовано получение полного списка заявок и отдельной заявки по идентификатору.

При успешном выполнении возвращается HTTP 200 OK. Если заявка с указанным идентификатором отсутствует, возвращается HTTP 404 Not Found.

#### 5.3. Назначение исполнителя

Для назначения исполнителя используется отдельный PATCH-маршрут:

`/api/repair-requests/{id}/assignee`

Пример тела запроса:

```json
{
  "assigneeUserId": 7
}
```

После назначения исполнителя сервер возвращает обновлённую заявку.

#### 5.4. Изменение статуса

Для изменения статуса используется отдельный PATCH-маршрут:

`/api/repair-requests/{id}/status`

Пример тела запроса:

```json
{
  "status": "InProgress"
}
```

Поддерживаются следующие статусы:

- `New` — новая заявка.
- `InProgress` — заявка находится в работе.
- `Closed` — заявка закрыта.
- `Cancelled` — заявка отменена.

Переход в статус `InProgress` без назначенного исполнителя запрещён. При нарушении этого правила API возвращает HTTP 409 Conflict.

### 6. Валидация входных данных

Для проверки входных данных используются атрибуты Data Annotations.

Реализованы следующие ограничения:

- Название заявки должно содержать от 5 до 80 символов.
- Описание должно содержать от 10 до 500 символов.
- Идентификатор аудитории должен быть больше нуля.
- Идентификатор исполнителя должен быть больше нуля.
- Статус должен соответствовать одному из четырёх допустимых значений.

При нарушении ограничений сервер возвращает HTTP 400 Bad Request с описанием ошибок валидации.

### 7. Обработка ошибок

В API предусмотрена обработка основных HTTP-ошибок:

| Код | Описание |
|---|---|
| 400 | Некорректные входные данные |
| 404 | Заявка не найдена |
| 409 | Нарушение бизнес-правил |
| 500 | Внутренняя ошибка сервера |

Для обработки непредвиденных исключений при создании заявки используется конструкция try-catch.

Ошибки записываются через ILogger. В журнал выводится краткая информация об операции, идентификаторе аудитории и типе исключения.

Клиенту возвращается безопасный ответ без раскрытия stack trace и внутренних подробностей приложения.

Для проверки обработки HTTP 500 временно использовалась имитация исключения `InvalidOperationException`. После проверки тестовая имитация была удалена.

### 8. Тестирование API

Тестирование выполнялось с помощью curl через терминал macOS.

#### 8.1. Создание заявки

Отправлен POST-запрос с корректными данными.

Результат: HTTP 201 Created. Заявка успешно создана, ей присвоены идентификатор 1 и номер 1001.

#### 8.2. Получение списка заявок

Отправлен GET-запрос:

`GET /api/repair-requests`

Результат: HTTP 200 OK. Сервер вернул список заявок.

#### 8.3. Получение заявки по идентификатору

Отправлен GET-запрос:

`GET /api/repair-requests/1`

Результат: HTTP 200 OK.

При запросе несуществующей заявки с идентификатором 999 сервер вернул HTTP 404 Not Found.

#### 8.4. Назначение исполнителя

Для заявки с идентификатором 1 был назначен исполнитель с идентификатором 7.

Результат: HTTP 200 OK. Поле `assigneeUserId` получило значение 7.

#### 8.5. Изменение статуса

Заявка с назначенным исполнителем была переведена в статус `InProgress`.

Результат: HTTP 200 OK.

#### 8.6. Проверка бизнес-правила

Создана вторая заявка — «Не работает микрофон». Исполнитель для неё не назначался.

При попытке перевести заявку в статус `InProgress` сервер вернул HTTP 409 Conflict.

Сообщение сервера: «Нельзя начать выполнение без назначенного исполнителя».

#### 8.7. Проверка валидации

Были выполнены запросы с некорректными значениями:

- Название заявки длиной менее 5 символов.
- Описание длиной менее 10 символов.
- Значение `classroomId = 0`.
- Недопустимый статус `Waiting`.

Во всех случаях сервер вернул HTTP 400 Bad Request с описанием ошибки.

#### 8.8. Проверка обработки внутренней ошибки

Для проверки временно было вызвано исключение `InvalidOperationException`.

Сервер вернул HTTP 500 Internal Server Error и безопасное сообщение:

«Не удалось создать заявку».

В журнале приложения появилась запись:

`CreateRepairRequest failed; classroomId=205; error=InvalidOperationException`

Stack trace и внутренние сведения клиенту не передавались.

После проверки тестовый механизм был удалён.
