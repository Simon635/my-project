# Курсовая записка
## Система учёта заявок на ремонт мультимедийного оборудования

**Выполнил:** Дудин Семен Дмитриевич  
**Группа:** ТРИС-2-23  
**Дисциплина:** Б1.В.ДЭ.01.02.02 — РИС и Web  
**Учебный год:** 2026/2027

## 1. Назначение системы

Разрабатываемая система предназначена для учёта заявок на ремонт мультимедийного оборудования в учебных аудиториях. Она позволяет регистрировать неисправности, назначать ответственных исполнителей и отслеживать ход выполнения ремонтных работ.

## 2. Функциональные возможности

В системе предусмотрены следующие основные возможности:

- авторизация пользователей;
- просмотр списка заявок;
- создание новых заявок диспетчером;
- указание аудитории и описания неисправности;
- назначение исполнителя;
- изменение статуса заявки;
- разграничение доступа в зависимости от роли пользователя;
- хранение информации в PostgreSQL.

Предусмотрены роли диспетчера и техника. Диспетчер регистрирует заявки и назначает исполнителей. Техник работает с назначенными ему заявками и изменяет их статусы.

## 3. Используемые технологии

Клиентская часть разработана с использованием Vue 3, JavaScript и Vite. Серверная часть реализована на ASP.NET Core 10 Web API. Для взаимодействия с базой данных применяется Entity Framework Core 10. В качестве системы управления базами данных используется PostgreSQL 16. Для аутентификации применяется Cookie Authentication.

## 4. Архитектура и организация данных

Приложение построено по клиент-серверной архитектуре. Клиентская часть отправляет HTTP-запросы к серверному API. Сервер выполняет проверку входных данных и прав доступа, взаимодействует с базой данных и возвращает результат клиенту.

Основные сущности базы данных:

- пользователи;
- аудитории;
- заявки на ремонт.

Для связей между сущностями используются первичные и внешние ключи. Статусы заявок включают New, InProgress, Closed и Cancelled.

## 5. Безопасность

Доступ к функциям системы предоставляется после авторизации. Права пользователя определяются его ролью. Сервер проверяет полномочия при выполнении операций. Пароли хранятся в виде хешей. Доступ техника ограничен заявками, назначенными этому исполнителю. Пользовательский ввод отображается без небезопасной интерпретации HTML.

## 6. Проверка работоспособности

В ходе лабораторных работ проверялись сборка и запуск приложения, взаимодействие frontend и backend, выполнение запросов к PostgreSQL, авторизация пользователей и разграничение доступа.

Сквозной сценарий включает создание заявки диспетчером, назначение техника и перевод заявки в статус InProgress. Результат проверялся в пользовательском интерфейсе, через HTTP-ответы API и непосредственно в базе данных. Дополнительно проверено сохранение данных после перезапуска серверного приложения.

## 7. Известные ограничения

При сборке backend выводится предупреждение NU1510, не препятствующее работе приложения. Для локального запуска API используется порт 5001, так как порт 5000 занят системным сервисом macOS. При создании заявки необходимо выбирать существующую аудиторию.

## 8. Заключение

Реализованы основные операции с заявками, хранение данных в PostgreSQL, авторизация и разграничение доступа по ролям. Работоспособность основных сценариев проверена в ходе лабораторных работ. Проект подготовлен к демонстрации и предзащите.
