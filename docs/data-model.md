# Модель данных

## 1. Словарь проекта

| Термин курса | Термин моей темы                 |
| ------------ | -------------------------------- |
| Ticket       | RepairRequest — заявка на ремонт |
| Site         | Classroom — аудитория            |
| User         | User — пользователь              |
| Assignee     | Техник, назначенный исполнителем |

Главный объект проекта называется `RepairRequest`. В API используется путь `/api/repair-requests`.

Далее эти термины используются одинаково во всех документах.

## 2. Сущность RepairRequest

`RepairRequest` — главный объект системы, заявка на ремонт мультимедийного оборудования.

| Поле              | Ключ         | Назначение                     |
| ----------------- | ------------ | ------------------------------ |
| `id`              | PK           | Машинный идентификатор заявки  |
| `number`          | —            | Человеческий номер заявки      |
| `title`           | —            | Заголовок заявки               |
| `description`     | —            | Описание неисправности         |
| `status`          | —            | Текущий статус заявки          |
| `classroomId`     | FK           | Ссылка на аудиторию            |
| `createdByUserId` | FK           | Пользователь, создавший заявку |
| `assigneeUserId`  | FK, nullable | Назначенный техник             |

`id` и `number` — разные поля.

`id` является техническим первичным ключом и используется системой для однозначной идентификации записи.

`number` является человеческим номером заявки, который отображается пользователю.

При создании заявки `assigneeUserId` может отсутствовать, потому что исполнитель назначается отдельным действием.

## 3. Сущность Classroom

`Classroom` — справочник аудиторий.

| Поле   | Ключ | Назначение                   |
| ------ | ---- | ---------------------------- |
| `id`   | PK   | Идентификатор аудитории      |
| `name` | —    | Название или номер аудитории |

В `RepairRequest` хранится только `classroomId`, а название аудитории хранится в `Classroom`.

## 4. Сущность User

`User` — пользователь системы.

| Поле    | Ключ | Назначение                 |
| ------- | ---- | -------------------------- |
| `id`    | PK   | Идентификатор пользователя |
| `login` | —    | Логин пользователя         |
| `name`  | —    | Имя пользователя           |
| `role`  | —    | Роль пользователя          |

Используются три роли:

* `Teacher` — преподаватель;
* `Dispatcher` — диспетчер;
* `Technician` — техник.

## 5. Статусы

В системе используются четыре значения статуса:

| Код          | Значение  |
| ------------ | --------- |
| `New`        | Новая     |
| `InProgress` | В работе  |
| `Closed`     | Выполнена |
| `Cancelled`  | Отменена  |

В API и базе данных используются именно английские коды.

## 6. Связи

### Classroom — RepairRequest

Одна аудитория может иметь много заявок.

```text
Classroom 1 ─────────── N RepairRequest
```

Связь:

```text
RepairRequest.classroomId → Classroom.id
```

### User — RepairRequest: автор

Один пользователь может создать много заявок.

```text
User 1 ─────────── N RepairRequest
```

Связь:

```text
RepairRequest.createdByUserId → User.id
```

### User — RepairRequest: исполнитель

Один пользователь может быть назначен исполнителем многих заявок.

```text
User 1 ─────────── N RepairRequest
```

Связь:

```text
RepairRequest.assigneeUserId → User.id
```

У новой заявки исполнитель может отсутствовать:

```text
assigneeUserId = NULL
```

## 8. Проверка 3НФ

Название аудитории хранится в сущности `Classroom` один раз. `RepairRequest` содержит внешний ключ `classroomId`, а не текстовое название аудитории.

При переименовании аудитории изменяется одна строка в `Classroom`, поэтому название не дублируется в заявках.

Информация о пользователях также хранится в `User`, а заявка содержит только внешние ключи `createdByUserId` и `assigneeUserId`.

Таким образом, данные справочника и пользователя не дублируются в каждой заявке.
