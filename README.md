# Система учёта заявок на ремонт мультимедийного оборудования

ФИО: Дудин Семен Дмитриевич  
Группа: ТРИС-2-23

## Описание проекта

Веб-приложение для учёта заявок на ремонт мультимедийного оборудования. Пользователи могут просматривать обращения и создавать заявки с указанием аудитории и описанием неисправности.

## Стек технологий

- Vue 3
- JavaScript
- Vite
- ASP.NET Core 10 Web API
- Entity Framework Core 10
- PostgreSQL 16
- Cookie Authentication

## Клиентское приложение

Клиентская часть находится в каталоге `frontend`.

### Требования

- Node.js 22 или совместимая актуальная LTS-версия
- npm

### Установка зависимостей

Из корня репозитория выполните:

```bash
cd frontend
npm install
```

### Запуск в режиме разработки

```bash
npm run dev
```

После запуска откройте адрес, указанный в терминале Vite. Обычно это:

http://localhost:5173/

### Production-сборка

```bash
npm run build
```

Готовые файлы сборки создаются в каталоге `frontend/dist`.

## Лабораторная работа №8 — REST API заявок на ремонт

Реализован REST API для создания, просмотра и обработки заявок на ремонт мультимедийного оборудования.

### Доступные endpoints

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/api/repair-requests` | Создание заявки |
| GET | `/api/repair-requests` | Получение списка заявок |
| GET | `/api/repair-requests/{id}` | Получение заявки по ID |
| PATCH | `/api/repair-requests/{id}/assignee` | Назначение исполнителя |
| PATCH | `/api/repair-requests/{id}/status` | Изменение статуса |

### Статусы заявок

- `New` — новая заявка.
- `InProgress` — выполняется.
- `Closed` — закрыта.
- `Cancelled` — отменена.

Перевод заявки в статус `InProgress` без назначенного исполнителя запрещён.

### HTTP-коды

- `200` — запрос выполнен успешно.
- `201` — заявка создана.
- `400` — ошибка валидации входных данных.
- `404` — заявка не найдена.
- `409` — конфликт бизнес-правил.
- `500` — внутренняя ошибка сервера.

### Хранение данных

На данном этапе заявки хранятся в оперативной памяти приложения (In-Memory). После перезапуска сервера данные сбрасываются. Подключение PostgreSQL предусмотрено на следующих этапах разработки.

### Postman

Коллекция запросов находится в `postman/Lab-08.postman_collection.json`.

Для импорта открой Postman → Import → выбери JSON-файл коллекции.

## Лабораторная работа №9 — PostgreSQL и SQL

Подготовлена реляционная схема базы данных системы учёта заявок на ремонт.

### Структура базы данных

Созданы три таблицы:

- `classrooms` — справочник аудиторий;
- `users` — пользователи системы;
- `repair_requests` — заявки на ремонт.

Настроены первичные и внешние ключи, ограничения целостности и индексы для поиска по статусу, аудитории и дате создания.

Для поля `status` разрешены четыре значения: `New`, `InProgress`, `Closed`, `Cancelled`.

### SQL-файлы

- `db/schema.sql` — создание таблиц, связей, ограничений и индексов;
- `db/seed.sql` — тестовые данные;
- `db/queries.sql` — запросы с фильтрацией, сортировкой, JOIN и GROUP BY.

### Проверка

Схема и запросы проверены на PostgreSQL 16.4.

В тестовую базу добавлены 3 аудитории, 3 пользователя и 4 заявки. Проверено ограничение CHECK: база отклоняет недопустимый статус `Done`.

На данном этапе PostgreSQL подготовлен отдельно от серверного приложения. Интеграция базы данных с ASP.NET Core ещё не выполнена.

## Лабораторная работа №10 — Entity Framework Core и PostgreSQL

Выполнена интеграция ASP.NET Core Web API с PostgreSQL через Entity Framework Core 10 и провайдер Npgsql.

- Создан `AppDbContext` и настроены сущности `RepairRequest`, `Classroom`, `User`.
- Создана миграция `InitialCreate` в каталоге `backend/Migrations`.
- Реализовано хранение заявок в PostgreSQL вместо оперативной памяти.
- API поддерживает создание, получение, назначение исполнителя и изменение статуса заявки.
- Строка подключения хранится через .NET User Secrets и не включается в репозиторий.
- Проверено сохранение заявки после перезапуска ASP.NET Core.

Подробный отчёт: [Лабораторная работа №10](docs/reports/lab-10.md).


## Лабораторная работа №11 — Аутентификация и разграничение прав

Реализована аутентификация пользователей и разграничение прав доступа по ролям.

- Добавлен вход, проверка текущего пользователя и выход из системы.
- Используется Cookie Authentication.
- Реализована проверка ролей Dispatcher и Technician.
- Диспетчер может создавать заявки и назначать исполнителей.
- Техник может изменять статус только назначенной ему заявки.
- Пароли хранятся в хешированном виде.
- Проверена защита от несанкционированных запросов и XSS.

### Endpoints авторизации

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/api/auth/login` | Вход в систему |
| GET | `/api/auth/me` | Информация о текущем пользователе |
| POST | `/api/auth/logout` | Выход из системы |

### Проверки безопасности

- Неавторизованный доступ возвращает HTTP 401.
- Запросы с недостаточными правами возвращают HTTP 403.
- Проверено создание и назначение заявок диспетчером.
- Проверено изменение статуса назначенной заявки техником.
- Проверен запрет изменения неназначенной заявки.
- Проверено хешированное хранение паролей.
- Проверено безопасное отображение пользовательского ввода.
